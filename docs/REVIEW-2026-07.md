## ② 良い点

1. **入口一本化の設計**（手動貼付・手入力・将来のショートカット自動送信がすべて `POST /api/meals`）。入力手段を増やしてもビジネスロジックが分岐しない。ゼロから設計してもこうする。
2. **`raw_json` の全保存**。AIの解析結果原文を必ず保持しているため、スキーマ変更・再解析・商品DB照合の後付けがいつでも可能。これがあるので「将来の拡張性」の大半は既に担保されている。
3. **RLSの徹底**。全テーブル4操作のポリシー + トリガー関数のEXECUTE剥奪までやり切っており、Supabase advisorsの警告ゼロ。anon keyが漏れても他人のデータには触れない。
4. **`daily_summaries` のトリガー集計**。日次表示・カレンダー・将来のAI分析が全てO(日数)で済む。10万件時代への備えが最初からある。
5. **実戦で鍛えられたバリデーション**。ChatGPT出力の揺れ（date+time分割・1桁時刻・キー名のアンダースコア省略・配列・英語recognition_type）を実際に踏んで全て吸収済み。この資産は書き直すと失われる。
6. **マイグレーションのコード管理**（5本連番）とCI（lint/tsc/build）が初日から回っている。

## ③ 問題点（重要度順）

### P1: 書き込みがアトミックでない（データ整合性）
`POST /api/meals` は meals をINSERT後に ingredients をINSERTする2段階で、後者が失敗しても前者は残る。ユーザーがエラーを見てリトライすると**食事が二重登録**される。PATCHは ingredients を全削除→再INSERTのため、途中失敗で**食材が消失**する。配列登録も逐次INSERTで、途中失敗時に「検証はall-or-nothingなのに保存は部分的」という矛盾が起きる。Postgres関数（RPC）1つで解決できる。

### P2: 廃止予定APIへの構造的依存（戦略リスク）
認証ガードが `middleware.ts`（Next.js 16で非推奨）に依存している。後継の `proxy.ts` はNode.jsランタイム専用で、Cloudflare（OpenNext）が未対応 — つまり**Next.js 17に上げた瞬間にビルドが壊れる可能性のある構造**。さらにページ側は `user!.id` の非nullアサーション8箇所でミドルウェアの成功を盲信しており、ミドルウェアが機能しないと500エラーになる。Next公式も「ミドルウェア認証は楽観的チェックに留めよ」という立場であり、レイアウト層での認証チェックに移すのが本筋。

### P3: テストがゼロ（保守性）
`validation/meal.ts`（ChatGPT揺れ吸収の中核・今後も揺れのたびに触る）、`score.ts`、`targets.ts`、`date.ts` は純関数でテスト容易性が高いのに1本もテストがない。今までの「揺れ対応」はすべて手動確認であり、**次の揺れ対応が過去の揺れ対応を壊しても気付けない**。

### P4: 履歴画面の上限100件（スケール）
`meals/page.tsx` が `limit(100)` の全件取得。約1ヶ月分で頭打ちになり、それ以前の記録が見えなくなる。10万件構想と矛盾する唯一の画面。

### P5: スコアの歴史的整合性（設計欠陥）
カレンダーの日次スコアが「現在の目標値」で全期間を再計算している。体組成計連携で目標値は自動更新されるため、**過去の日のスコアが目標変更のたびに書き変わる**。「あの日は85点だった」が信用できない。目標値をその日のサマリーにスナップショットすべき。

### P6: DB型定義が手書き（乖離リスク）
`types/database.ts` が手書きで、実際にbrand/recognition_type追加時に手動同期が必要だった。`supabase gen types` で自動生成すべき。

### P7: その他
- `error.tsx` / `loading.tsx` 不在（エラー時に素のNext.jsエラー画面）
- MealJsonImport / WeightJsonImport にほぼ同一の貼付→検証→プレビューロジックが重複
- `validation/meal.ts` に体重スキーマも同居（ファイル名と内容の不一致）
- APIのエラーが `console.error` すらされずWorkersログで追えない
- ショートカット自動送信（Phase 5）に冪等性の設計がない（リトライ=二重登録）

## ⑤ データベース改善案

現行スキーマは**全面変更不要**。以下の追補のみ行う。

1. **`daily_summaries` に目標値スナップショット列を追加**（★★★★）
   `target_calorie_kcal / target_protein_g / target_fat_g / target_carbohydrate_g / target_salt_g` を追加し、`refresh_daily_summary()` トリガー内で `users` から現在値をコピー。スコア計算は保存された目標値を使う。「その日の目標に対してどうだったか」が永続化される。
2. **`meals.meal_group_id uuid` を追加**（★★★★・JSON v2と同時）
   配列登録された料理群（=1回の食事イベント）を紐付ける。テーブル分割（meal_events親テーブル化）はやらない — daily_summariesが集計を担っており、グループ表示だけならIDで十分。ゼロから設計するなら親子2テーブルにするが、現状からの移行コストに見合う利益がない。
3. **`register_meal(jsonb)` / `update_meal(uuid, jsonb)` のPostgres関数化**（★★★★★）
   meals + ingredients の書き込みを1トランザクションに。API側は関数を呼ぶだけになり、コードも減る。
4. **将来テーブル（設計のみ・マイグレーションはまだ書かない）**
   - `products`（brand + product_name + JANコード + 公式栄養成分）: 商品照合Phase用
   - `coach_comments`（AIコーチ生成結果のキャッシュ）: Phase 4用
   - `api_keys`（key_hash・last_used_at）: Phase 5用 — SPECIFICATION.md 16.2の設計を維持
   - `purchases`（食費: 金額・店舗・レシートOCR由来フラグ）: mealsに金額を混ぜず別テーブルにする。食事と支出はライフサイクルが違う（外食1回=食事複数・支出1件）
5. **インデックスは現状で十分**。10万件でも `(user_id, eaten_at desc)` でDashboard/履歴クエリはインデックススキャンで済む。追加するとすれば `meals(meal_group_id)`（追加時に同時作成）。

## ⑥ JSON改善案（v2仕様）

後方互換を完全維持（v1のJSONは今後も全て受理）した追補型:

```jsonc
{
  "schema_version": 2,            // 省略時はv1として解釈
  "datetime": "...",
  "meal_type": "夕食",
  "menu_name": "素材を生かしたキーマカレー",
  "brand": "無印良品",
  "recognition_type": "商品",
  "confidence": 95,
  // --- v2追加 ---
  "portion_ratio": 0.5,           // 食べた割合（半分残した=0.5）。省略時1.0
  "people_count": 2,              // 取り分け人数。省略時1
  "store": "ローソン新宿店",       // 店舗・購入場所
  "memo": "",                     // ユーザーメモ（AIは空で出す）
  "photo_url": null,              // 将来の写真連携用（Phase 6）
  // 栄養素は「皿全体」の値。アプリ側で ratio/people を掛けて摂取量を算出
  "calorie_kcal": 850, "protein_g": 40, "...": "..."
}
```

**設計判断**: 栄養値は「皿全体」をAIに出させ、摂取量への換算（× portion_ratio ÷ people_count）はアプリ側で行う。AIに換算までさせると検算不能になるため。`daily_summaries` トリガーは換算後の値を合計する（mealsに換算後の値を保存し、皿全体の値はraw_jsonに残る、が最も単純）。

| 層 | 担当 | 理由 |

## ⑩ セキュリティ改善案

現状の評価: **個人利用の範囲では十分堅い**。RLS全テーブル・service_role不使用・トリガーEXECUTE剥奪済み・シークレットのコミットなし・SQLはsupabase-jsのパラメータ化のみ・XSSはReactのエスケープ + raw_jsonの生描画なし・CSRFはCookie(SameSite=Lax) + JSON Content-Type（プリフライト必須）で実質不成立。

公開範囲を広げる前にやること（★★★、現時点では急がない）:
1. メール確認の有効化（現在はMVPでオフ）
2. セキュリティヘッダ（CSP・X-Frame-Options・Referrer-Policy）
3. APIキー実装時: キーは発行時1回表示・ハッシュ保存・失効機能・キー単位のレート制限（60req/h）
4. Supabase Authの漏洩パスワード保護オプション有効化

## ⑪ パフォーマンス改善案

**10万件・写真数千枚に対する評価**:
- 食事10万件 ≒ 90年分（1日3食）であり、実際は5年で約5,500件。**DB設計は現状で余裕**。インデックスと daily_summaries が正しく効く。
- 唯一の欠陥は履歴の `limit(100)`（→ ★★★★★ #4で解消）。
- 写真数千枚: DBには**絶対に入れない**。設計は「Supabase Storage（無料1GB・RLS連携が楽）にオリジナル + 表示用は幅800px程度のサムネイル生成」。数千枚×平均200KB(サムネイル)=1GB以内に収まる。超えたらCloudflare R2（egress無料・Workersと同居）へ移行。**今は設計のみ**。
- Rechartsのバンドルサイズは現状許容。グラフ画面が増えたら dynamic import。
